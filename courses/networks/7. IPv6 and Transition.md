# 7. IPv6 and Transition

## 7.1 IPv4 vs IPv6

### 7.1.1 Motivations for Moving to IPv6

- IPv4 address exhaustion: the 32-bit address space provides approximately 4.3 billion addresses, a limit reached by IANA in February 2011 and by most regional registries shortly after
- NAT as a stopgap: Network Address Translation extended the usable life of IPv4 by allowing multiple devices to share a single public address, but introduced complexity, broke end-to-end connectivity, and complicated certain protocols
- Limitations of NAT: complicates peer-to-peer applications, VoIP, and IPsec; requires stateful devices that become single points of failure
- IPv6 address space: 128-bit addresses providing approximately 3.4 × 10³⁸ unique addresses, designed to eliminate scarcity
- Simplified header: fixed 40-byte header replacing the variable-length IPv4 header, intended to improve forwarding efficiency
- Removal of header checksum: eliminated in IPv6 to reduce per-hop processing, on the assumption that link-layer and transport-layer checksums are sufficient
- Native support for autoconfiguration: Stateless Address Autoconfiguration allows devices to configure their own addresses without a DHCP server
- Designed-in multicast: IPv6 replaces broadcast with multicast for network functions, reducing unnecessary traffic
- Adoption pace: despite the exhaustion of IPv4 addresses, IPv6 deployment has been gradual; as of the mid-2020s, IPv6 traffic represents roughly 40–45% of Google's user traffic globally, with significant variation by country

### 7.1.2 IPv6 Format and Header Fields

- Fixed header length: 40 bytes, compared to the variable 20–60 bytes of IPv4
- Header fields:
  - Version: 4 bits, set to 6
  - Traffic Class: 8 bits, equivalent to the IPv4 DSCP and ECN fields; used for QoS marking
  - Flow Label: 20 bits, intended to identify packets belonging to the same flow for consistent treatment; use cases include ECMP hashing and QoS
  - Payload Length: 16 bits, indicating the length of the payload following the fixed header
  - Next Header: 8 bits, identifying the type of the following header, whether an extension header or an upper-layer protocol; replaces the IPv4 Protocol field
  - Hop Limit: 8 bits, equivalent to the IPv4 TTL field; decremented by each router
  - Source Address: 128 bits
  - Destination Address: 128 bits
- Extension headers: optional headers chained via the Next Header field; used for routing, fragmentation, authentication, encapsulating security payload, and hop-by-hop options
- Fragmentation in IPv6: only the source host may fragment packets; routers do not fragment; Path MTU Discovery is therefore mandatory
- Hop-by-Hop Options header: the only extension header that must be processed by every router on the path; used sparingly due to performance implications
- Comparison with IPv4: IPv6 removes the header checksum, options field, and IHL field; adds the Flow Label; moves fragmentation entirely to the source

### 7.1.3 IPv6 Addressing

- Notation: eight groups of four hexadecimal digits separated by colons; consecutive groups of zeros may be replaced by "::" once per address
- Address length: 128 bits, typically divided into a 64-bit network prefix and a 64-bit interface identifier
- Address types:
  - Unicast: identifies a single interface; includes global unicast, link-local, and unique local addresses
  - Multicast: identifies a group of interfaces; all nodes in a group receive the packet; replaces broadcast
  - Anycast: assigned to multiple interfaces; the packet is delivered to the nearest one according to routing metrics
  - No broadcast: broadcast does not exist in IPv6; its functions are handled by specific multicast groups
- Global unicast addresses: routable on the internet; currently allocated from the 2000::/3 prefix
- Link-local addresses: automatically configured on every interface; prefix fe80::/10; used for neighbour discovery and routing protocol communication; not routable beyond the local link
- Unique local addresses: prefix fc00::/7; analogous to IPv4 private address ranges; routable within a site but not on the public internet
- Interface identifier generation: can be derived from the MAC address using the EUI-64 process, randomly generated for privacy, or assigned manually
- Privacy extensions: defined in RFC 4941; generate temporary, randomised interface identifiers to prevent tracking based on a stable address
- Neighbour Discovery Protocol: replaces ARP; uses ICMPv6 messages for address resolution, router discovery, and duplicate address detection
- Prefix delegation: routers advertise prefixes to hosts via Router Advertisement messages, enabling Stateless Address Autoconfiguration
- DHCPv6: stateful address assignment and option distribution; can be used alongside or instead of SLAAC depending on deployment requirements
- Subnetting: the standard allocation unit for a LAN segment is a /64, regardless of the number of hosts; larger prefixes are used for point-to-point links (/127 recommended by RFC 6164) and loopbacks (/128)

### 7.1.4 IPsec in IPv6

- Relationship to IPv4 IPsec: IPsec was originally developed alongside IPv6 and was mandatory to implement in early IPv6 specifications; RFC 6434 (2011) downgraded it to a recommendation, aligning with IPv4 practice
- Extension header integration: IPsec in IPv6 uses the Authentication Header and Encapsulating Security Payload extension headers rather than separate encapsulation
- Authentication Header: provides integrity and origin authentication for the IP packet; does not provide confidentiality; identified by Next Header value 51
- Encapsulating Security Payload: provides confidentiality, integrity, and optional authentication; identified by Next Header value 50
- Transport mode: protects the payload of the IP packet; the original IP header remains visible
- Tunnel mode: encapsulates the entire original packet within a new IP packet; used for VPNs and gateway-to-gateway protection
- Internet Key Exchange version 2: the standard protocol for negotiating IPsec security associations; supports IPv6 natively
- Practical deployment: end-to-end IPsec between arbitrary hosts remains uncommon; IPsec is more widely deployed at gateway level for VPNs
- Interaction with NAT: IPsec in transport mode is incompatible with NAT modifying IP headers; NAT Traversal encapsulates ESP within UDP to work around this; less relevant in IPv6 environments where NAT is not expected

### 7.1.5 IPv6 Routing

- Routing protocols adapted for IPv6:
  - OSPFv3: defined in RFC 5340; extends OSPF to support IPv6 prefixes; runs directly over IPv6; supports multiple address families
  - IS-IS for IPv6: extended via TLVs to carry IPv6 reachability information; a single IS-IS process can handle both IPv4 and IPv6
  - RIPng: defined in RFC 2080; a simple distance-vector protocol for IPv6; limited to small networks due to the 15-hop diameter constraint
  - BGP-4 with IPv6 extensions: uses Multiprotocol BGP extensions defined in RFC 4760 to advertise IPv6 prefixes; the same BGP session can carry both IPv4 and IPv6 Network Layer Reachability Information
- Static routing: fully supported in IPv6; link-local addresses are commonly used as next-hop addresses for static routes on point-to-point links
- Route aggregation: the large IPv6 address space and hierarchical allocation policy are designed to facilitate aggregation and limit routing table growth
- Routing table growth: despite design intent, the global IPv6 BGP table has grown alongside the IPv4 table; multihoming and traffic engineering practices contribute to deaggregation
- Neighbour Discovery and routing: Router Advertisement messages carry prefix information and default gateway information, replacing the need for a separate default gateway configuration on hosts
- Recursive DNS server advertisement: can be included in Router Advertisement messages via the RDNSS option defined in RFC 8106, reducing dependence on DHCPv6 for basic host configuration

### 7.1.6 Persistent Vulnerabilities in IPv6

- Neighbour Discovery Protocol attacks: the absence of built-in authentication makes NDP susceptible to neighbour cache poisoning, analogous to ARP spoofing in IPv4
- Rogue Router Advertisements: an attacker can send unsolicited Router Advertisement messages to redirect traffic or cause denial of service; mitigated by RA Guard defined in RFC 6105
- SEND (Secure Neighbour Discovery): defined in RFC 3971; uses cryptographically generated addresses and RSA signatures to authenticate NDP messages; rarely deployed due to complexity
- Extension header abuse: chains of extension headers can be used to evade firewalls and intrusion detection systems that do not parse them fully; some implementations drop packets with unusual extension header combinations
- Fragmentation attacks: because only the source fragments in IPv6, reassembly at intermediate devices is not expected; however, overlapping fragment attacks and tiny fragment attacks remain possible and can bypass security controls
- Amplification via multicast: certain multicast groups are reachable by all nodes; an attacker with access to the local link can generate significant traffic by sending to these groups
- Transition mechanism vulnerabilities: tunnelling protocols used during IPv4/IPv6 coexistence introduce additional attack surfaces
  - 6to4 and Teredo: automatic tunnelling mechanisms that can bypass perimeter security controls by encapsulating IPv6 within IPv4
  - Dual-stack exposure: hosts running both IPv4 and IPv6 may be reachable via IPv6 even when the organisation's security policy was designed around IPv4 only
  - IPv6 traffic ignored by IPv4-only security tools: firewalls and IDS systems that do not inspect IPv6 may pass IPv6 traffic without applying any policy
- Address scanning: the large address space makes random scanning impractical, but attackers can target well-known addresses (router link-locals, anycast addresses) and use DNS or other discovery methods to enumerate hosts
- Privacy address limitations: privacy extensions reduce tracking but do not prevent an attacker already on the local network from observing traffic
